# [기술 검토] Windows·macOS·Linux 지원과 Rust 채택 여부

## 배경
현재 MVP는 C#/.NET, WPF, SSH.NET, VtNetCore, Windows named pipe와 DPAPI를 사용한다. Windows뿐 아니라 macOS와 Linux까지 지원하는 방향을 검토한다. 사용자는 Rust에도 개인적 관심이 있으며, 기술적 이유가 있다면 채택을 선호한다.

## 목표
기존 C# 선택의 근거를 재평가하고, 유지·부분 전환·Rust 중심 전환을 비교한 의사결정 문서를 작성한다. Rust 재작성이나 특정 UI 프레임워크를 미리 확정하지 않는다.

## 비교 기준
- SSH 인증/키/MFA, PTY와 VT 호환성, 메모리 및 입력·출력 수명 관리
- 세 OS의 UI, 접근성, IME, 터미널 렌더링과 크기 변경
- 로컬 IPC 인증과 사용자 경계, 비밀 저장 및 배포 방식
- MCP SDK 호환성, 정상/비정상 종료, 개발·유지보수 및 이전 비용
- 기존 보안 계약과 검증 자산 재사용, 개인적 학습 동기의 비용/편익

## 완료 기준
- 현재 Windows 의존 부분과 플랫폼 공통 부분을 목록화한다.
- C# 유지/크로스플랫폼 UI, Rust 코어 병행, Rust 중심 구조의 장단점을 근거와 함께 비교한다.
- 기술 선택에 결정적인 미확인 항목과 필요한 작은 검증을 제시한다.
- 채택/보류 결론 및 선택 시 단계별 이전·배포·검증 범위를 제시한다.
- 코드 변경 없이 먼저 설계 판단을 리뷰한다.

관련: docs/design.md. 기존 사용자 셸 계약이나 인증정보 정책을 언어 변경을 이유로 완화하지 않는다.
