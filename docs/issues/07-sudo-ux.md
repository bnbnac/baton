# [설계] sudo가 필요할 때 사용자가 확인·개입하는 흐름

## 사용자 요구
sudo가 실제로 필요할 때마다 사용자에게 요청하고 확인받는 경험을 검토한다. 현재는 하네스 대화에서 실행 승인을 받고 sudo -n으로 수행하며, 추가 인증이 필요하면 새 셸을 사용자가 준비해야 한다.

## 선택한 우선안
사용자는 ‘실행 승인만’과 ‘직접 비밀번호 입력까지’ 중 쉬운 방식을 선택하도록 했다. 우선 기존 하네스 대화에서 최종 명령을 승인받고 sudo -n으로 실행하는 흐름을 명확히 한다. 추가 인증이 필요하면 사용자가 새 셸에서 준비하고 전달한다. 별도 승인 팝업, 전달 후 비밀번호 입력 통로, 프롬프트 자동 탐지 기능은 우선 범위에서 제외한다.

## 분리해야 할 두 절차
1. 정확한 명령·인자·목적에 대한 이번 실행의 사용자 승인.
2. 원격 sudo가 요구하는 사용자 인증.
실행 승인을 받았다고 비밀번호 인증을 대신하지 않으며, 인증 캐시가 있다고 실행 승인을 생략하지 않는다.

## 설계 질문
- 현재 대화의 승인 대상 서버/세션, 최종 명령, 1회 실행 범위가 사용자에게 명확한지 확인한다.
- 단순한 우선안이 실제 사용에서 부족한 경우에만 Baton 알림/팝업 또는 일시적 소유권 전환을 별도 검토한다.
- 직접 인증을 허용한다면 모델의 입력과 사용자 입력이 섞이지 않는 전환 절차가 필요하다.
- 조용한 출력이나 특정 문자열만으로 비밀번호 프롬프트를 신뢰할 수 있다고 가정하지 않는다.

## 제약
- 현재 방식은 모델에 제공하는 운영 지침이다. 문구만으로 매 실행 승인 준수를 강제할 수는 없다. 하네스가 지원하는 실행 승인과 Baton 자체 강제 차단의 차이를 명시하고, 강제 보장이 필요하다면 별도 설계 대상으로 구분한다.
- 모델이 사용자 비밀번호를 요청·보관·대리 입력하는 방식은 제외한다.
- 자동 sudo -v 갱신, sudoers 변경, NOPASSWD 설정으로 흐름을 우회하지 않는다.
- 기존 ‘전달 후 사용자 입력 금지’와 ‘별도 승인 UI 없음’을 변경할 필요가 있다면 범위를 명시하고 설계 결정 후 진행한다.
- 현재 -n 누락 수정과 이 확장 설계를 혼동하지 않는다.

## 완료 기준
현재 구조에서 승인 요청→사용자 결정→1회 실행→결과 또는 추가 인증 안내가 이해되는지 사용자 흐름을 작성한다. 승인 거절/실패/연결 종료 시 무단 실행이나 자동 재시도가 없어야 한다. 직접 인증 통로가 나중에 필요해지면 별도 설계에서 민감 입력·출력의 MCP 공개 경계를 검증 가능하게 정의한다.

구현 착수는 별도 결정한다.
