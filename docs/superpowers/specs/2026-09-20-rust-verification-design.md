# Baton Rust 전환 검증 기준

작성일: 2026-09-20. 상태: 사용자 승인된 시험 설계. 아래 테스트는 아직 작성하거나 실행하지 않았다. 실행 순서와 단계별 적용 범위는 [단계 0 실행 계획](../plans/2026-09-20-rust-phase-0.md)에서 시작한다.

상위 설계: [Rust 전환 설계](2026-09-20-rust-transition-design.md).

사용자 요구: 테스트를 엄격하게 수행한다. Windows 먼저 검증·배포하고 macOS/Linux는 해당 OS에서 실제 검증한 뒤 순차 지원한다.

## 1. 판정 원칙

- Rust 새 구현은 C# 통과 결과를 승계하지 않는다. 기본 기능뿐 아니라 기존 버그 재현 사례를 새 테스트로 옮긴다.
- 정상 경로, 거부 경로, 중간 실패를 각각 시험한다. 핵심 계약은 화면 메시지뿐 아니라 mock transport 송신 횟수·실제 서버 수신·IPC 응답에서 확인한다.
- 재현 가능한 동기화 장벽과 fake clock으로 경쟁 순서를 고정한다. 임의 sleep 하나로 race를 시험했다고 판단하지 않는다.
- 실제 UI·SSH·배포·하네스 시험을 단위 테스트로 대체하지 않는다. skip, 보류, 환경 부재는 통과가 아니다.
- 실패한 시험이 재시도에서 통과해도 flaky로 남긴다. 원인 규명 없이 retry 횟수를 늘려 통과시키지 않는다.
- 요구사항 ID, 테스트 경로, 실제 명령, commit, 도구 버전, 실행 환경, 결과를 연결한 인수표를 작성한다. 커버리지 수치만으로 완료를 판정하지 않는다.
- 실제 사용자 서버 대신 격리 fixture를 사용한다. 사용자의 인증정보·터미널 원문을 시험 보고서에 수집하지 않는다.

| IPC-01 | 틀린 secret·다른 OS 사용자·느슨한 권한·잘못된 버전 | 연결/배정 거부, 원인 코드 구분, 다른 앱 instance 비밀 사용 불가 |
| IPC-02 | partial frame·256KiB 초과·EOF·read8/요청16 경계 | 메모리 상한 준수, 불완전 요청은 미실행, 읽기 대기가 입력을 막지 않음 |
| LIFE-01 | 앱 없이 MCP 시작→앱 실행→종료→재실행 | 초기화/목록/status 유지, 새 연결·미배정, 이전 ID/입력/출력 자동 복원 없음 |
| LIFE-02 | A 어댑터 EOF·강제 종료, 사용자 회수 셸 포함 | A의 AgentOwned 셸만 닫힘. 다른 연결·회수된 사용자 셸은 계약대로 유지 |
| LIFE-03 | 앱 정상/강제 종료와 OpenSSH 비교 | 독립 관찰 접속으로 PTY·PID·start time 추적. 일반 작업과 nohup+disown 구분 |
| LIFE-04 | TCP 정상 close·server kill·패킷 blackhole | 서로 다른 조건으로 보고. blackhole을 즉시 탐지했다고 주장하지 않음 |
| MCP-01 | 실제 stdio 초기화·도구 스키마·취소·동시 호출 | v2 계약과 오류 코드 일치, stdout에 진단/터미널 원문이 섞이지 않음 |
| SUDO-01 | 목표만 제시한 승인·거절·인증 필요·사용자 처리·재전달 | 승인 전 최종 -n 명령, 승인 없이 실행 없음, 실패 후 자동 재실행 없음 |

OWN·IN·OUT·IPC의 거부 시험은 오류 문자열뿐 아니라 전송/반환 데이터가 실제로 없었는지 검사한다. 에러를 반환한 뒤 이미 명령을 전송한 경우는 실패다.

## 3. 경쟁 조건과 모델 시험

세션의 작은 참조 상태 모델을 테스트용으로 둔다. 구현 함수를 다시 호출해 기대값을 계산하지 않고, 권한·세대·공개 구간 규칙으로 기대 효과를 산출한다.

이벤트 집합: 연결 생성/단절, 전달 시작/완료, 회수 시작/완료, 입력 수락/쓰기 시작/쓰기 종료, 수신 출력, 읽기 취소, resize, 세션 close, 앱 close. 가능한 순서와 무효 순서를 모두 생성한다.

- 매 변경: property test 1,000개 시드, 시드당 최대 200이벤트. 실패 시 seed와 최소 이벤트열을 보관한다.
- 릴리스 후보: 10,000개 시드, 시드당 최대 500이벤트. 회수·쓰기·종료의 고정 장벽 시나리오를 각각 100회 반복한다.
- 항상 검사할 불변식: 동시에 일반 입력 주체는 하나, 오래된 epoch 효과 0회, 잘못된 연결 조회 0바이트, 중복 요청 효과 최대 1회, Closed 이후 쓰기 0회, 큐와 버퍼 상한 준수.
- 모형 시험은 실제 스레드·네트워크 통합 시험을 대신하지 않는다. transport에 쓰기 지연·부분 실패·닫힘을 주입해 실제 async 코드에서도 동일 조건을 시험한다.

핵심 검사가 작동하는지 확인하기 위해 테스트용 변이도 사용한다. owner 검사 제거, epoch 검사 제거, private 출력을 public에 추가, 중복 입력 재전송, 재접속 시 기존 ID 재사용의 다섯 변이는 각각 관련 테스트가 반드시 실패해야 한다. 변이 코드는 제품에 남기지 않는다.

## 4. 퍼징과 부하

릴리스 후보에서는 다음 네 입력면을 각각 최소 30분 퍼징한다. 발견한 실패 입력은 최소화한 뒤 영구 회귀 fixture로 남긴다. 동일 seed만 반복 실행해 새로운 탐색이라고 보고하지 않는다.

1. IPC 길이·JSON·문자열·취소 프레임.
2. UTF-8 decoder·UTF-16 cursor·ring 경계.
3. 터미널 조회 추적기·길이 제한·분할 ANSI와 xterm hook 통합.
4. 전달·회수·종료·입력·resize 이벤트열.

실제 xterm/WebView는 브라우저 기반 생성 입력 시험과 OS UI 시험을 함께 수행한다. Rust 퍼징 결과만으로 WebView의 메모리·parser 안전성을 주장하지 않는다.

2시간 soak에서 연결 32개·SSH 세션 16개 한도를 사용한다. 두 개 이상의 시험 서버에 로그 출력·간헐적 명령·resize·탭 전환·회수·재전달을 섞는다. 정상 소비 부하와 의도적인 UI 과부하 종료를 분리해 판정한다.

- 정상 소비 부하: 16개 셸에서 각각 초당 1KiB 출력을 지속하고 주기적으로 짧은 burst를 추가한다. 데이터 섞임·교착·입력 중복 0건을 요구한다.
- 과부하: UI ack를 정지하고 정해진 큐 상한을 넘어서는 출력을 보내, 무제한 축적 대신 명시적 종료가 되는지 확인한다.
- 메모리: 앱·WebView·어댑터를 합산해 주기 측정한다. warm-up 20분 이후 20분 구간별 중앙값을 기록하고 마지막 구간이 첫 안정 구간보다 20% 초과하면 원인 분석 전 출시하지 않는다. 이 기준은 누수 부재의 증명이 아니라 조사 기준이다. 앱 내부 큐/버퍼 한도는 별도로 정확히 검사한다.
- 반복 수명: 앱/어댑터/세션 생성·종료를 100회 수행해 남은 프로세스·소켓·시험 endpoint·컨테이너가 없는지 확인한다. 사용자의 기존 프로세스나 컨테이너는 정리 대상에 포함하지 않는다.

긴 시험은 중단·진행 상태 조회가 가능한 별도 프로세스로 실행한다. 결과를 기다리는 동안 사용자에게 진행 상태를 알릴 수 있게 하고, 실제 수행 시간과 중단 여부를 보고한다.

## 5. 실제 Windows 배포본 인수

개발 서버만 통과해서는 출시하지 않는다. Node/.NET/Rust 개발 도구 없이 실행 가능한 배포본으로 검사하되, 필요한 WebView 런타임 등 제품 의존성과 설치 조건을 문서화한다.

필수 수동·자동 조합:

- 비밀번호·키·MFA 입력 및 취소, 호스트키 대조, 일반 사용자 셸 진입.
- 한글 조합·조합 중 회수·붙여넣기·키 반복·선택/복사·마우스, 화면 배율 100/150/200%.
- 같은 서버의 실행/로그 셸과 별도 서버 셸을 번갈아 보고 대상 혼동이 없는지 확인.
- vi와 interactive top의 진입·사용·resize·종료, Ctrl+C 후 같은 셸의 새 명령.
- 앱 종료 후 어댑터 offline 응답, 재실행 후 새 전달. 실제 Claude Desktop과 Codex는 각각 검증한 버전을 기록.
- SUDO-01은 실제 모델 동작 시험으로 관찰한다. 통과는 해당 실행 사례의 증거이며 미래 모든 모델 출력의 강제 보장이 아니다.

사용자가 보류한 Desktop/CLI 동시 연결 시험은 임의로 재개하지 않는다. 그 조합과 대화별 격리는 미검증/미지원으로 표시하며, 단일 하네스 시험을 대신 근거로 쓰지 않는다. 단일 하네스의 실제 검증도 설치·계정·설정 변경이 필요한 경우 사용자 환경에 맞는 실행 범위를 먼저 확인한다. 다른 OS 사용자 경계 시험은 격리 VM/시험 계정 환경에서 수행하며 사용자의 실사용 PC에 임의 계정을 만들지 않는다.

macOS/Linux는 같은 인수표를 해당 OS에서 수행한다. Unix socket 권한·peer uid, WebView 의존성, 한글 입력·DPI, 정상/강제 종료를 추가 확인한다. Windows 출시 완료가 나머지 OS 지원 완료를 뜻하지 않는다.

## 6. 출시 차단 조건과 증거

다음 중 하나라도 있으면 해당 범위의 출시를 차단한다.

- 다른 연결 접근, 비공개 저장 기록 노출, 오래된 입력/중복 명령 실행, 비밀번호·키·MFA·endpoint secret 로그 노출.
- 핵심 OWN/IN/OUT/IPC/LIFE 시험의 실패·skip·미해결 flakiness.
- 자동 응답 경로가 일반 사용자 입력 차단을 우회하거나, 공개 API로 구현하지 못해 임의 내부 패치에 의존하는 상태.
- 실제 배포본 인증·한글 입력·기본 전체 화면 앱·앱 오프라인 흐름 미확인.
- 재현 가능한 crash·교착·지속 메모리 증가·다른 세션의 잘못된 종료.

기능 지원에서 명시적으로 제외한 하네스 조합·아직 출시하지 않는 OS는 미지원으로 남길 수 있다. 핵심 실패를 ‘알려진 제한’으로 이름만 바꿔 출시하지 않는다.

보고서는 commit·lockfile, OS/WebView/하네스 버전, 시험 명령·실행 시간, 통과/실패/skip 수, 시드·최소 재현, fixture 정리 결과를 포함한다. 시험 전용 데이터의 화면·응답만 증거로 남기고 실제 사용자 세션 원문을 수집하지 않는다.

## 7. 테스트를 구현 계획으로 옮기는 규칙

각 단계 계획에 위 ID를 연결하고, 기능 코드보다 먼저 실패하는 회귀 시험을 제시한다. 테스트-only 모델이나 fixture가 구현과 같은 실수를 복제하지 않도록 외부 관찰값을 사용한다. 규칙마다 담당 테스트가 없는 경우 단계 완료로 표시하지 않는다.

전체 시험을 작은 문구 수정 때마다 반복하지 않는다. 코어 변경은 관련 단위·모형·통합 시험, UI 변경은 입력·렌더링·WebView 시험을 실행한다. 릴리스 후보에는 전체 필수 인수·퍼징·soak를 수행하며 이후 변경이 영향을 주는 시험은 다시 실행한다.
