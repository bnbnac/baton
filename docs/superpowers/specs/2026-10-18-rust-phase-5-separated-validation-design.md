# Phase 5: 목적별 부하·전환·네이티브 UI 검증 설계

상태: 분리 방향에 대한 사용자 동의를 반영한 설계안. 문서 검토 대기이며 구현·시험 실행 승인을 뜻하지 않는다.

## 1. 목적과 현재 증거

목적은 메모리 안정성, 반복 소유권 전환, 실제 Windows UI 조작을 각각 검증하되 대화형 에이전트의 판단·도구 왕복 시간을 제품 성능으로 오인하지 않는 것이다. 사용자는 엄격한 시험과 기존 실패 증거 보존을 원하며, 목적별 분리안을 선택했다.

기존 2시간 시험은 실제 7,200초와 전환 120회를 수행했으나 메모리 기준을 넘었다. 자동화 연결을 분리한 60분 진단에서는 같은 증가를 재현하지 못했지만 계측 영향의 인과관계나 2시간 통과를 증명하지 않았다. 이후 네이티브 smoke 세 번은 모두 회차 제한 시간에 실패했다. 세 번째는 선택·resize·회수까지 검증했으며 전달 전에 시간 예산이 소진됐다.

최대화 상태의 접근성 요소 클릭이 빗나가는 현상은 본문 캡처 좌표 입력과 복원 상태 대조로 좁혔다. 소유권 처리 코드의 결함은 확인하지 못했다. 현재 문제를 해결하기 위해 제품 코드를 추측으로 수정하지 않는다.

## 2. 범위와 비동등성

세 시험은 같은 후보 앱·어댑터와 fixture image로 별도 실행한다. 원래 시험의 실패 기록과 판정기는 변경하지 않는다. 이 문서는 새로운 부분 검증의 정의이며 기존 통합 soak를 소급 통과시키는 대체 판정이 아니다.

| 시험 | 입증할 항목 | 입증하지 못하는 항목 |
|---|---|---|
| M: 2시간 자동화 분리 부하 | 고정 UI 상태에서 연결·출력·audit·메모리 유지 | 반복 UI 전환 중 장기 메모리 안정성 |
| F: 120회 자동 전환 | 실제 프런트엔드와 MCP/서버 사이의 반복 전환 기능 | 자연 상태 메모리 안정성, 2시간 지속성, 네이티브 입력 경로 |
| N: 짧은 네이티브 UI 확인 | 실제 창·입력으로 선택·resize·회수·목표 연결 전달 | 장기 안정성, 분당 전환 처리량, 모든 DPI/창 배치 |

세 결과를 합쳐도 **반복 전환을 포함하는 2시간 자연 상태 메모리 안정성**은 미완료다. 해당 항목과 기존 Phase 5 출시 차단은 유지한다. 향후 결합 시험의 방법은 별도로 설계·검토해야 하며 이 문서에서 면제하지 않는다.

제품 기능·프로토콜·배포 설정·사용자 서버는 변경 대상이 아니다. 기존 미완성 fuzz 파일을 수정·실행·커밋하지 않으며 dirty Cargo workspace에서 후보를 재빌드하지 않는다.

## 3. 공통 실행 구조

기존 Node 실행기, MCP stdio 어댑터, Windows 프로세스 감독기, OS 메모리 sampler, Docker OpenSSH fixture, 출력 oracle을 재사용한다. 시험별 시나리오와 판정기를 분리하고 단일 모호한 `passed`로 세 조건을 합치지 않는다.

데이터 흐름은 시험 실행기 → 실제 앱 UI 또는 MCP → SSH fixture이며, 판정에는 UI 관측뿐 아니라 MCP 상태·실제 원격 stty·서버 audit 파일을 사용한다. 상태를 직접 덮어쓰는 테스트 전용 제품 API를 만들지 않는다.

- 32개 고유 MCP 연결, 16개 SSH 세션, 별도 localhost 서버 두 개에 8개씩 배치한다.
- 각 실행의 신규 증거 디렉터리, owner UUID, PID·시작 시각, commit, 소스/바이너리 SHA-256, image ID를 고정한다. 증거 경로가 존재하면 실행을 거부한다.
- OS·Node·WebView·Playwright 버전을 기록한다. 비교 묶음의 후보 바이너리·이미지·버전이 달라지면 같은 조건이라고 합산하지 않는다. setup 시도 후 버전이 달라졌음을 알게 된 경우에도 측정을 시작하지 않는다.
- 구조화 출력의 세션 표식·순서를 검사하고 모든 공개 구간에서 누락·중복·혼합을 거부한다. 회수 중 비공개 출력은 공개 누락으로 세지 않는다.
- 원시 관측과 summary를 따로 보존하고 검증기는 둘의 일치를 확인한다. 실행기 자체의 성공 플래그만 신뢰하지 않는다.
- 오류·취소·진행 상태를 조회할 수 있어야 한다. 실패 시 자동 재실행하거나 다음 장시간 시험을 시작하지 않는다.
- 정상 종료 코드 0, 어댑터 32개 EOF, WebView 자손 종료 감사, 강제 정리 없음, 소유 프로세스·컨테이너 0을 모두 요구한다. 안전을 위한 강제 정리가 필요했다면 자원은 정리하되 해당 종료 검사는 실패로 남긴다.
- 정리는 owner label+이름/ID, 프로세스 PID+시작 시각을 대조한 대상에만 적용한다. 이미지 태그는 비교 실행 사이에 보존하고 더 이상 필요 없을 때 현재 ID가 기록과 같아야 제거한다.

## 4. M: 2시간 자동화 분리 부하

Playwright는 초기 세션 연결·전달·첫 탭 표시까지만 사용한다. 이후 연결을 닫고 참조를 해제한 뒤 16세션 출력 준비를 확인하여 측정을 시작한다. 측정 중 탭/창/소유권 상태를 의도적으로 바꾸지 않으며 Playwright/CDP 재접속, JS/DOM 진단, 강제 GC는 하지 않는다. 예상 밖 세션·소유권 변화는 실패다.

실제 정상 부하는 최소 7,200초다. 셸별 최소 1KiB/s 구조화 출력과 30초마다 4KiB burst를 유지한다. 60초 간격으로 모든 셸에 고유 audit 명령을 보내고 같은 send_text request_id를 한 번 재전송한다. 120회·1,920개 서버 효과를 최종 파일과 대조하여 중복·누락 0을 확인한다. 연결 health와 세션 신원도 같은 주기로 확인한다.

OS 메모리와 디버깅 포트 TCP 연결을 30초 주기로 관측한다. 앱 1개·renderer 1개·어댑터 32개의 신원과 Job 내 프로세스 구성을 확인한다. 정상 구간 모든 표본의 debugger established는 0이어야 한다. 표본 사이 접속 부재까지 단일 TCP snapshot으로 증명했다고 주장하지 않는다. 준비용 debug listener와 준비 단계의 영향은 한계로 기록한다.

기존 메모리 판정 조건을 유지한다.

- 정상 구간 표본만 사용하고 endpoint/과부하/종료 관측을 섞지 않는다.
- 첫 20분을 제외하고 20~40, 40~60, 60~80, 80~100, 100~120분의 중앙값을 기록한다.
- 30초 주기를 목표로 하며 양 끝 공백과 표본 간격은 최대 45초, 각 안정 구간은 기존 판정기와 동일하게 최소 30표본을 요구한다. 실제 개수·누락·간격을 보고한다.
- 앱·Job 내 WebView·어댑터 합계 private bytes와 working set 각각 마지막/첫 안정 구간 비율 ≤1.20이어야 한다. 역할별 수치도 기록한다.
- 비율 초과는 메모리 검사 실패다. 부하 자체가 유효하다면 이것만으로 이후 과부하·정상 종료 검사를 생략하지 않는다.

정상 구간의 증거를 먼저 고정한 다음에만 Playwright를 재연결해 기존 과부하 대조를 수행한다. 32KiB×40회 정상 소비 대조 후 대상 UI ack 차단 시 그 세션만 명시적으로 닫히고 다른 15개 세션은 생존해야 한다. 부하가 무효이면 과부하 생략 사유를 기록하고 정상 종료는 시도한다.

M의 통과 명칭은 `detached_static_load_passed`다. 기존 통합 soak 또는 Phase 5의 통과로 표시하지 않는다.

## 5. F: 120회 자동 전환 기능

같은 32/16/2 구성을 준비하고 Playwright를 유지한다. M과 같은 셸별 출력 발생률·burst를 사용하되 회수 중 비공개 구간과 공개 구간을 분리해 출력 증거를 판정한다. 기존 실제 프런트엔드 조작 경로를 사용한다. 각 회차는 다음 순서를 따른다.

1. round modulo 16의 세션 탭을 선택하고 표시된 전체 세션 ID를 대조한다.
2. 선택된 터미널의 geometry가 750ms 이상 안정된 값을 기준으로 레이아웃 폭을 바꾼다. 실제 GeometryObserver 경로를 통과하여 MCP geometry와 서버 stty가 함께 달라져야 한다. 이것은 OS 창 크기 변경 검사가 아니다.
3. 회수 버튼을 눌러 user_owned, 증가한 epoch, 공개 stream 없음으로 전환됐는지 확인한다.
4. 현재 adapter의 인덱스에 16을 더한 연결(modulo 32)을 실제 목록에서 선택·전달한다. 새 owner·증가 epoch·새 stream과 이전 owner의 할당 해제를 확인한다.
5. 모든 세션의 health와 공개 출력 연속성을 검사한다. 같은 회차의 고유 audit를 전체 16세션에 중복 request_id로 보내 최종 120회·1,920효과를 대조한다.

총 120회가 검증돼야 한다. 완료된 회차의 마지막 상태를 확인한 뒤 다음 회차를 시작하며 분당 실행을 강제하지 않는다. 이 **횟수 기반 실행은 새로운 설계 선택**이며, 실제 소요 시간과 회차 간격을 보고하되 2시간 부하나 기존 분당 전환 빈도와 동등하다고 하지 않는다.

각 상태 대기는 최대 45초로 제한하고, 최초 실패에서 중단·정리한다. 성공하지 못한 조작을 자동 반복하거나 실패 회차를 제외해 120회를 채우지 않는다. 이 시험에는 대화형 소비자의 55초 합산 마감을 적용하지 않는다. Playwright가 부착된 상태이므로 메모리는 참고값이며 M의 판정에 사용하지 않는다.

F의 통과 명칭은 `transition_cycles_passed`다. UI 클릭 성공만으로 통과시키지 않고 MCP와 서버 증거를 모두 요구한다.

## 6. N: 짧은 네이티브 UI 확인

동일 32/16/2 목록 환경을 준비하고 Playwright를 분리한 뒤 computer-use로 수행한다. 구현 시점에도 적용되는 computer-use 관측·입력 규칙을 준수한다. 직접 OS 입력 helper나 관측 없는 클릭 반복으로 대체하지 않는다.

필수 두 시나리오는 복원 창과 최대화 창이다. 서로 다른 세션을 선택해 전체 ID를 대조하고, 창 크기 변화가 MCP/서버 stty에 반영되는지 검사한다. 각 시나리오에서 회수 후 **현재 선택과 다른, 사전에 지정된 MCP 연결**을 목록에서 선택·전달한다. epoch/stream/이전 owner 검증은 F와 동일하다.

최대화·복원 전환 완료를 새 화면에서 관측하고 실제 본문 screenshotId를 식별한다. 첫 캡처를 본문으로 가정하지 않는다. 최대화 상태의 요소 클릭을 신뢰하지 않고 새 화면의 버튼 좌표를 사용한다. 선택 목록은 실제 표시 ID와 키보드 선택 결과를 대조한다. 즉시 반환된 접근성 텍스트와 화면이 다르면 추가 관측 또는 MCP 결과로 확인하며 성공을 추정하지 않는다.

분당 속도 또는 합산 55초는 N의 제품 합격 조건이 아니다. 사용자가 응답하거나 에이전트가 관측하는 시간은 제품 지연으로 측정하지 않는다. 무한 대기를 방지하는 실행 전체 900초 watchdog은 유지하고 만료는 불완료로 기록한다. 실제 입력 후 MCP 상태 확인 대기는 45초 이내로 제한한다. 실패 후 입력을 무관측 반복하지 않는다.

N의 통과 명칭은 `native_cases_passed`다. 이 결과는 현재 배율·OS·창 환경에만 적용하며 기존 배율/IME/입력 인수 시험을 대체하지 않는다.

## 7. 증거와 종합 판정

각 summary에는 시험 종류, 구성, 시간, 수행량, 중단 사유, 단계별 상태를 구분한다. 부분 수행을 정상 완료로 승격하지 않는다. 검증 결과는 다음 범위를 명시한다.

| 결과 필드 | 의미 |
|---|---|
| evidenceValid | 원시 증거·시간·신원·해시·필수 관측을 대조할 수 있음 |
| scopePassed | 해당 M/F/N의 모든 조건이 통과함 |
| phase5Acceptance | 항상 false: 이 설계만으로 전체 인수를 승인하지 않음 |
| combinedTransitionMemory | unverified: 반복 전환 중 2시간 자연 상태 메모리 안정성 미완료 |

통합 보고서는 M/F/N 결과를 각각 표시한다. 실패는 해당 시험 및 전체 진행 상태에 남긴다. 필수 증거 누락은 설명 가능한 검증 실패로 반환하고 성공 파일을 만들지 않는다. 과거 세 smoke, 기존 2시간 메모리 실패, 60분 진단은 역사적 증거로 연결하고 덮어쓰지 않는다.

## 8. 구현과 검증의 다음 단계

이 설계 문서 승인 후 구현 계획을 작성한다. 실행기는 기존 native soak/soak/detached 진단의 공통 자원 관리와 oracle을 우선 재사용하되 역사적 결과의 판정 로직은 바꾸지 않는다. 제품 변경 없이 시험 코드·절차·문서만 대상으로 한다.

판정기의 검증은 짧은 실행을 2시간으로 오인하는 경우, 표본 공백/GC/CDP 개입, 잘못된 owner/epoch/stream, 이전 owner 미해제, 잘못된 서버 크기, audit 중복/누락, 불완전 120회, 정상 종료·정리 실패, 서로 다른 바이너리/이미지를 합치는 경우를 거부하는 데 집중한다. 단순 구현 복제 테스트는 만들지 않는다.

실행 준비는 관련 단위 검사 → 짧은 자동 실행 사전 검사 → 두 네이티브 시나리오 → 정식 F/M 실행 순서로 계획한다. 사전 검사는 각 범위의 축소 실행이며 정식 통과로 세지 않는다. 구현 계획에는 고정 입력과 실행 명령, 중단·정리·독립 검증 방법을 구체화한다. 사전 검사 통과가 다음 장시간 실행을 자동 승인하지 않으며 실패 시 동일 시험을 자동 재실행하지 않는다.

이 문서 작성으로 새 시험이나 heartbeat는 시작하지 않는다. 문서 검토 후에도 원래 결합 조건은 별도의 미완료 항목으로 남는다.
