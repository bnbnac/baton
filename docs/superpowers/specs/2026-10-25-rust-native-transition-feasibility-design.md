# 네이티브 연속 전환 실행 가능성 확인

상태: 준비안의 3회·60초 중단 조건을 사용자가 승인했고 구현 계획 작성을 요청했다. 구현 계획은 별도 문서로 검토하며 아직 새 진단을 구현/실행하지 않았다.

## 목적과 근거

디버깅 연결을 끊은 상태에서 실제 UI 전환을 분당 한 번 수행할 수 있는지 확인한다. 원래 결합 부하의 32연결/16세션/2서버, 2시간/120전환 조건을 줄여 통과시키는 시험이 아니다.

기존 `phase5-sampler-diagnostic-20261025`의 N 복원/최대화 실행은 각각 275.190/252.163초다. 입력 시작부터 receipt 접수까지 연결 선택만 40.857/46.658초이며, 다른 단계와 단계 사이 운영 시간도 필요하다. 이는 제품 응답 지연이 아니라 컴퓨터 제어·화면 확인·도구 왕복을 포함한다. 현재 방식의 분당 반복 가능성은 입증되지 않았다. 이번 준비에서 `@oai/sky` 초기화는 성공했으며 UI 입력은 수행하지 않았다.

## 방법 선택

- 선택한 방법: Computer Use로 실제 창/탭/연결 목록을 조작한다. Playwright는 준비에만 사용하고 측정 중 연결하지 않는다. 제품 변경 없이 실제 UI 경로를 검사하지만 대화 중단·포커스·왕복 지연에 취약하다.
- 최소 CDP 조작 도구: 반복하기는 쉽지만 새 도구와 디버깅 연결의 측정 영향을 구별해야 하므로 이번 범위에서 제외한다.
- 결합 시험 유예: 비용은 낮지만 장기 전환 메모리는 미검증으로 남는다. 이번 사용자 선택은 유예가 아니라 짧은 실행 가능성 확인이다.

## 제안 절차

1. 고정 제품/adapter/image를 재사용한다. 현재 바이너리 해시·환경을 확인하고 새 증거 경로 및 owner를 예약한다. 준비 중 컴퓨터 제어 사용 가능 여부를 먼저 확인한다. 기존 M/F/N 결과·판정기는 수정하지 않는다.
2. 같은 32/16/2 fixture를 준비한 뒤 Playwright를 분리한다. 실제 Baton 창을 관측해 정확한 대상 신원을 고정한다. 화면 관측 후 하나의 입력과 즉시 재관측을 수행하는 도구 규칙을 지킨다. 관측 없는 반복 입력 스크립트로 바꾸지 않는다.
3. 최대 3회, 세션 인덱스 **0→1→0**을 대상으로 탭 선택→크기 변경→회수→다른 연결 선택→전달을 수행한다. 같은 세션의 두 번째 전환은 현재 owner의 반대 연결로 돌아가야 한다. 최초 창 상태 준비는 별도로 기록한다.
4. 각 회차에서 화면의 전체 세션/연결 ID, MCP geometry와 서버 stty, user_owned와 epoch 증가, 새 owner/stream, 이전 owner 할당 해제를 검증한다. 기존 mailbox의 입력 시작 승인과 실제 screenshot receipt를 재사용한다. 시작 승인 전 입력하지 않는다.
5. **첫 회차부터 60초 내 회차 검증과 해당 audit/health를 끝내지 못하면 이후 회차를 생략하고 정상 종료한다.** 다음 시작은 이전 시작+60초보다 빠르지 않게 한다. 밀린 회차 몰아 실행·실패 제외·기한 연장·자동 재실행은 하지 않는다. 준비 포함 900초 상한과 기존 정상 종료/소유 자원 정리 절차를 유지한다. 정상 종료·정리 시간은 회차 시간과 분리한다.
6. 회차마다 전체16세션 audit 1효과씩, 전체32연결 health를 확인한다. 공개 stream 내부 출력 연속성·섞임을 검사하되 회수 시 미수신 꼬리 폐기는 승인된 계약에 따라 허용한다. 실패 시 수행된 부분만 기록한다.

## 증거와 판정

새 진단 실행기/판정기는 기존 N의 고정 1/2사례 계약을 변경하지 않고 별도로 둔다. 공통 준비·MCP·소유 자원 관리·mailbox·전환 검증을 재사용할 수 있지만 새 진단을 기존 N `scopePassed`로 판정하지 않는다. 구현 계획에서 수정 파일과 검증 재사용 범위를 명시한다.

시작 예정/실제 시작, 각 입력·접수·검증 완료, 회차 종료, 최대 회차 시간 및 실패 지점을 기록한다. OS 메모리·debugger 연결 관측은 30초 간격으로 남기되 짧은 수치에 2시간 memoryVerdict를 적용하지 않는다. 측정 중 CDP/JS/GC 개입은 금지하고 준비의 영향과 listener 존재는 기록한다.

보고는 `evidenceValid`, 완료 회차, `cadenceObserved`(세 회차 모두 예정 주기 내 완료 여부), `longRunReadiness: unproven`, `memoryAcceptance: not_evaluated`, `phase5Acceptance: false`를 구별한다. 시간 초과는 조작 경로의 운영 적합성 실패이며 곧바로 제품 성능 결함으로 분류하지 않는다. 세 회차가 빨라도 2시간 무중단 운영을 입증하지 않는다. 소유 자원 정상 종료·잔류0은 별도 필수 조건이다.

## 다음 결정

주기를 감당하지 못하면 같은 시험을 자동 반복하거나 분당 조건을 완화하지 않는다. 다른 조작 방법 또는 명시적인 검증 범위 변경을 논의한다. 세 회차를 완료해도 2시간 시험은 자동 시작하지 않고 운영 중단 위험과 실행 방법을 별도로 검토한다. 제품·Cargo·미완성 fuzz는 변경/실행하지 않는다.
