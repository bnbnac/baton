## 현재 목적과 진행 방향 — 2026-10-29 사용자 확인

사용 목적은 제품의 정식 출시가 아니라 **사용자 본인의 개인 사용**이다. 아래의 정식 출시 인수 목록을 개인 사용 시작의 일괄 선행 조건으로 적용하지 않는다. 기존 실패·미검증 항목은 보존하되, 이를 앱 사용 불가능이라는 뜻으로 설명하지 않는다. 정식 Phase 5 통과나 모든 환경의 안전성을 새로 선언한 것은 아니다.

초기화에서 보완한 것은 **진단 누락**이지 과거 제품 결함의 원인 해결이 아니다. 제한 환경에서의 연결 실패와 동일 소스의 호스트 통과는 [후속 보고서](rust-startup-followup-report.md)에 함께 기록돼 있다. 현재 진단은 시험 전용이며, 개인 사용 배포본이 동일한 상세 진단을 자동 수집한다고 가정하지 않는다. 실제 사용에서 재발하면 발생 시각·실행 파일·사용한 endpoint 경로·관측 오류부터 보존하고 필요한 진단 범위를 정한다. 인증정보나 터미널 원문을 수집하지 않는다.

메모리 코드 읽기는 다음 경로로 한정해 시작한다.

1. [output_pump.rs](../../rust/app/src-tauri/src/output_pump.rs): Rust 출력 전달·대기·작업 종료.
2. [terminal/bridge.ts](../../rust/app/src/terminal/bridge.ts)와 [sessions/view.ts](../../rust/app/src/sessions/view.ts): 채널 연결, 초기 출력 대기열, 세션별 객체 생성·제거.
3. [terminal.ts](../../rust/app/src/terminal/terminal.ts): 터미널 출력 처리와 dispose.

질문은 “누가 데이터를 보관하고, 상한은 무엇이며, 언제 참조/작업/구독을 해제하는가?”다. 이 파일들에 결함이 있다고 확정한 것은 아니다. WebView 내부 전체를 먼저 공부하거나 기존 성공 시험을 전부 반복하는 것을 해결의 전제조건으로 두지 않는다.

아래 감사 결과는 **정식 출시를 다시 목표로 삼을 때 참고할 기록**이다. 현재 우선순위는 이 절을 따른다. 새 시험·자동화 재개·제품 수정은 이번 정리에서 수행하지 않았다.

## 판단 기준

기준은 [승인된 검증 설계](../superpowers/specs/2026-09-20-rust-verification-design.md) §2–6 및 이후 명시 승인된 범위 변경이다. 보고서의 과거 pending 문장을 현재 할 일로 그대로 복사하지 않는다. 통과 범위, 후보 동일성, 실제 미실행, 실패 원인 미확정, 인수 방식의 결정 필요를 구분한다.

과거 실패는 보존하지만 영구 차단 자체가 목적은 아니다. 해당 실패의 원인·영향 또는 시험상의 한계를 근거로 분류하고, 현재 후보가 승인된 조건을 충족하는 증거를 갖춰야 한다. 새 통과 횟수만으로 미해결 flakiness를 지우지는 않는다.

## 회수 경계: 더 요구하지 않을 것과 계속 요구할 것

[2026-10-25 승인 결정](../superpowers/specs/2026-10-18-rust-phase-5-separated-validation-design.md#2026-10-25-승인-결정-즉시-권한-회수-유지)은 미수신 공개 꼬리 폐기를 허용한다. **그 완전 전달 미입증만을 출시 차단 사유로 쓰지 않는다.** 과거 `publicBoundaryCompleteness:unverified` receipt를 바꿀 필요도 없다.

반대로 옛 권한의 새 입력/응답 commit 거부, 사용자 제어 구간 비공개 출력 격리, 재전달 후 옛 epoch/stream 거부는 여전히 필수다. `commit_agent_response`와 bridge의 commit 재검사, 응답 commit 전 회수를 고정하는 `CommitGate` 시험이 존재한다. 해당 시험은 현재 후보 로그에서 통과했다. 따라서 이 부분을 막연히 “실제 IPC 증거 없음”으로 분류하는 것도 틀리다. 회수 전에 commit된 응답의 지연 도착 및 이미 시작된 쓰기의 효과는 승인된 의미와 구분한다.

## 정식 출시를 전제로 했던 조사 당시 권장 순서

1. 초기화 실패의 원인 분류를 먼저 진행한다. 핵심 IPC 실패가 실제 제품 수정으로 이어지면 후보와 후속 인수 범위가 달라지기 때문이다. 첫 단계는 기존 실패/진단 기록의 좁은 비교이며 새 장시간 반복이 아니다.
2. 그와 별도로 메모리 인수 방식을 명확히 결정한다. 단지 과거 실패가 남았다는 이유로 A/B 또는 자연 상태 시험을 자동 반복하지 않는다.
3. 정해진 후보를 기준으로 실제 미완료 fuzz/변이 및 환경·하네스 검증을 닫고, 최종 패키지와 요구사항 ID별 증거를 연결한다. 변경 없는 코어·인증·수명 결과는 영향을 검토해 재사용하며 일괄 재시험하지 않는다.

이 문서 작성으로 새 시험, 제품 수정, 후보 빌드, 출시 차단 해제 또는 자동화 재개를 수행하지 않았다.
